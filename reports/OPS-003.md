## 1. Kết Quả Thực Hiện

### 1.1. Mô Hình Schemas & Dữ Liệu Phục Hồi (`packages/shared/src/models/recovery.ts`)
- Định nghĩa các Zod schema và TypeScript types phục vụ quá trình phục hồi hệ thống:
  - `RecoveredTaskActionSchema`: Enum `['REQUEUED', 'FAILED']` thể hiện hành động xử lý task.
  - `RecoveredTaskItemSchema`: Thông tin task được phục hồi `{ taskId, previousStatus, newStatus, action, attempts, maxAttempts, runId, reason }`.
  - `CleanedRunItemSchema`: Thông tin run bị treo được dọn dẹp `{ runId, taskId, previousStatus, newStatus, pid, reason }`.
  - `RecoveryResultSchema`: Kết quả toàn diện của phiên phục hồi `{ recoveryId, trigger, recoveredTasks, cleanedRuns, releasedLocks, timestamp }`.
  - `RecoveryOptionsSchema`: Tùy chọn điều khiển phục hồi `{ trigger, autoRequeue, forceFailAll, lockId, releaseAllLocks, recordAudit }`.
  - `RecoveryStatusSchema`: Trạng thái gián đoạn đọc nhanh (read-only) `{ needsRecovery, runningTasksCount, activeRunsCount, heldLocksCount, runningTaskIds, activeRunIds, heldLockIds }`.
  - `RecoveryAuditSchema` & `CreateRecoveryAuditInputSchema`: Cấu trúc nhật ký kiểm toán phiên phục hồi.

### 1.2. Cơ Sở Dữ Liệu SQLite & Migration 015 (`packages/db/migrations/015_restart_recovery.sql`)
- Tạo bảng `recovery_audits` lưu vết mọi phiên phục hồi:
  - `id TEXT PRIMARY KEY`, `trigger TEXT NOT NULL`, `recovered_tasks_count INTEGER NOT NULL DEFAULT 0`, `cleaned_runs_count INTEGER NOT NULL DEFAULT 0`, `released_locks_count INTEGER NOT NULL DEFAULT 0`, `details TEXT NOT NULL DEFAULT '{}'`, `created_at TEXT NOT NULL`.
  - Chỉ mục: `idx_recovery_audits_created_at`, `idx_recovery_audits_trigger`.
- Xây dựng `RecoveryAuditRepository` (`packages/db/src/repositories/recovery-audit-repository.ts`):
  - Hỗ trợ `create`, `getById`, `getLatest`, `findAll(filter)`, `count()`.
  - Re-export qua `@ai-orchestrator/db`.

### 1.3. Dịch Vụ Phục Hồi Trung Tâm `RecoveryService` (`apps/orchestrator/src/services/recovery-service.ts`)
- Triển khai `RecoveryService` xử lý các tác vụ phục hồi toàn vẹn trong `db.transaction(...)`:
  - `checkInterrupted()`: Quét và trả về trạng thái task treo (`RUNNING`, `VERIFYING`), run treo (`RUNNING`, `PENDING`), và lock bị chiếm giữ.
  - `recover(options)`:
    - **Bước 1 — Giải phóng Locks**: Force release stale locks trong bảng `agent_locks` để dọn dẹp deadlock.
    - **Bước 2 — Dọn dẹp Runs**: Quét mọi run có status `RUNNING`/`PENDING`, cập nhật status sang `ERROR`, ghi nhận `finished_at = now`, `exit_code = 1`. Tạo checkpoint `recovery_interrupted` và event `run_interrupted` gắn với run, bảo đảm không xóa bất kỳ bản ghi lịch sử nào.
    - **Bước 3 — Kiểm tra & Requeue/Fail Task**:
      - Nếu `attempts < max_attempts` và không `forceFailAll`: Chuyển task `RUNNING`/`VERIFYING` sang `FAILED` rồi sang `READY` (requeue). Ghi nhận checkpoint `recovery_requeued`.
      - Nếu `attempts >= max_attempts` hoặc `forceFailAll`: Chuyển task sang `FAILED` dứt điểm, chống crash loop vô hạn. Ghi nhận checkpoint `recovery_failed`.
    - **Bước 4 — Reset Tài Nguyên**: Gọi `resourceQuotaManager.resetQuota()` khi có task/run được phục hồi.
    - **Bước 5 — Lưu Nhật Ký Kiểm Toán**: Lưu bản ghi phiên phục hồi vào bảng `recovery_audits`.

### 1.4. Tích Hợp Vào `TaskScheduler` (`apps/orchestrator/src/services/task-scheduler.ts`)
- Bổ sung `recoveryService` vào `TaskScheduler`.
- Cung cấp phương thức `scheduler.recover(options)` và `scheduler.getRecoveryStatus()`.
- Hỗ trợ tùy chọn `autoRecoverOnStartup` trong cấu hình khởi tạo scheduler.

### 1.5. Khởi Động Server & REST API Endpoints (`apps/orchestrator/src/server.ts`, `main.ts`, `routes/scheduler.ts`)
- Server production (`main.ts`) tự động kích hoạt `autoRecover: true` khi khởi động Orchestrator.
- Cung cấp các endpoint điều khiển phục hồi REST:
  - `POST /scheduler/recover` & `POST /api/scheduler/recover` & `POST /system/recovery`: Thực thi phục hồi theo yêu cầu.
  - `GET /scheduler/recovery/status` & `GET /api/scheduler/recovery/status` & `GET /system/recovery`: Truy vấn trạng thái phục hồi.

### 2.3. Bằng Chứng Tiêu Chí "Không mất lịch sử"
- Run bị gián đoạn lưu giữ 100% dữ liệu gốc: ID, attempt, started_at, các logs/events stdout/stderr đã phát trước đó.
- Cập nhật an toàn `finished_at = now`, `status = ERROR`, `exit_code = 1`.
- Ghi nhận checkpoint `recovery_interrupted` và event `run_interrupted`.
- `TaskHistoryService.getTaskRunHistory(taskId)` truy xuất đầy đủ: Attempt 1 (gián đoạn - ERROR) và Attempt 2 (chạy tiếp - SUCCESS) hiển thị tuần tự, không bị thất lạc bất kỳ sự kiện nào.

### 2.4. Bằng Chứng Tiêu Chí "Không chạy trùng"
- Stale lock trong `agent_locks` được dọn dẹp, loại bỏ nguy cơ deadlock.
- Task được đưa về `READY`, bảo đảm scheduler chỉ acquire tuần tự 1 task duy nhất tại một thời điểm (`concurrency = 1`).
- Khi scheduler đang chạy Attempt 2, mọi nỗ lực acquire task thứ hai đều bị chặn bởi `LOCK_HELD` hoặc `CONCURRENCY_LIMIT_EXCEEDED`.
- Mọi thao tác phục hồi thực thi trong `db.transaction(...)` đồng bộ của `better-sqlite3`.
